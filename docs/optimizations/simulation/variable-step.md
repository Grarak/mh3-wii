# Variable game step

## What the original does

MH3's logic advances in fixed steps of 1/30 s (a *tick*). Its main loop
(0x800401A8) counts VI retraces and runs one frame per two retraces at
60 Hz. Timers are frame counts (seconds × the fps float at 0x8065B4D0,
which is 30) counted down once per step; speeds, spins and eases are
amounts per step; periodic events test a global step counter
(`system_w+0xC`, 0x8065AA6C) with `% N == k`. NW4R's animations advance by
`FrameCtrl::smBaseUpdateRate` (0x80793628) per step.

## What the port does instead

Each logic step runs for the host time that really elapsed, as a scale of
the stock tick (`GameStep`, `runtime/include/game_step.h`):

- **The frame pacer** (`runtime/src/frame_pacer.cpp`, a C port of
  0x800401A8) measures the step on the host clock and calls
  `GameStep::Begin(s)`. It writes `s` into `smBaseUpdateRate`, so every g3d
  animation is continuous, and keeps the fps float at 30.
- **Tick sites** (`runtime/src/tick_sites.inc`, 316 entries): guest loads
  that feed an inline `x ± 1`, `x + k`, an ease `x += (goal − x) / d` or a
  decay `x *= f` are wrapped by the translator (`translation.tick_sites_path`
  in `recomp.yml`). Counters move by the whole ticks of the step; amounts,
  eases and decays are scaled (`d' = 1 / (1 − (1 − 1/d)^s)`, `f^s`).
- **Step counter sites** (`runtime/src/step_counter_sites.inc`, 299
  entries, generated by `scripts/step_counter_sites.py`): `% N == k` tests of
  the step counters pass once per N ticks.
- **Native ports** that scale their amounts (shells, enemy turning and
  gliding, player actions, root motion, particles, the camera) or run their
  bookkeeping once per whole tick (player timers, stamina, AI checks).
- **Game time between ticks** for visuals that are a function of the tick
  counter: Ceadeus's texture offset (0x803750E8, a sine of the counter) takes
  the counter plus the step's fraction of a tick, so it no longer holds and
  jumps at more than 30 steps a second (commit "Swing Ceadeus's texture
  offset at the step's game time").
- **Discrete versus continuous**: motion and visual amounts are continuous;
  timers, steps-in-state counts and periodic triggers stay on whole ticks.
  The ones that may look lumpy at high frame rates are listed in
  [variable-step.md](variable-step.md).

`MH3_VARIABLE_STEP=0` restores fixed steps in development builds.

## Why

The goal is a frame rate limited only by the hardware, with the game
running at the same speed. A fixed 1/30 s step ties the logic to 30 Hz;
interpolating drawn states between fixed steps would smooth the picture but
keep the logic and input handling at 30 Hz. With a variable step every
presented frame shows a new simulation state, and the game thread limiter
([render thread](../threading/render-thread.md)) keeps the steps even.

The step affects more than motion. Input, for example: at the variable
step before the input ports, holding the d-pad for 120 ticks produced
1,517-1,628 repeats instead of 36, and the name-entry keyboard typed the
key that opened it ([variable step](variable-step.md)).

## Example

Shells move once a step through two helpers; the port takes both amounts
over the step's length (`runtime/src/shell_motion.cpp`):

```cpp
// v += d * s for the f32 vectors at v and d.
void AddScaled(uint32_t v, uint32_t d, float s) {
    for (uint32_t i = 0; i < 12; i += 4)
        MemoryInline::FlatWriteFloat32(v + i, MemoryInline::FlatReadFloat32(v + i) + MemoryInline::FlatReadFloat32(d + i) * s);
}

void ShellRateAddGPort(CpuContext* ctx) {
    const uint32_t shell = ctx->gpr[3];
    const float s = float(GameStep::Scale());
    AddScaled(shell + kPosition, shell + kVelocity, s);
    AddScaled(shell + kVelocity, shell + kAcceleration, s);
}
```

`VecAddInPlace` (0x80073FCC) is a general helper with about 200 callers, so
its port scales the addend only at the 30 return addresses that move by a
rate (`kRateCalls`).

## Applying it to another Wii game

Generic: `GameStep`, the translator's load hooks for tick sites and step
counter sites, the frame pacer approach, and the probes that find
step-dependent state: `MH3_STEP_PROBE` runs a step of 1.0 against two of
0.5 from the same RAM and reports what differs, and the write-watch build
finds the guest code that writes an address.

Game-specific: the sites, which is most of the work. MH3 needed 316 tick
sites, 299 step counter sites and dozens of ports. Expect every system to
have per-step amounts: physics, AI, camera, input repeats, UI animation,
sound timers. Decide per site whether it is continuous or discrete, check
each port against the original at the stock step (`MH3_PORT_CHECK`), and
settle-probe each map. A load that looks like a per-step amount may not be
one: the enemy update (0x801382A0) eases a height offset and sets the
model's offset from it each step, and the site at 0x801389C0 had taken that
load for a turn rate. Scaled by the step, Jhen Mohran's drawn height
followed the step's length, a flicker of the whole monster; removing the
site fixed it (commit "Keep a monster's height offset whole at any step
length"). A game whose logic already uses a time delta (some
do for parts of their code) needs fewer sites.
